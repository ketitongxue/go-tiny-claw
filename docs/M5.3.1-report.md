## 2. ReportMode 设计

新增 `internal/delivery/policy.go`：

```go
type ReportMode string

const (
    ReportModeQuiet   ReportMode = "quiet"
    ReportModeCompact ReportMode = "compact"
    ReportModeVerbose ReportMode = "verbose"
)
```

`ParseReportMode` 仅接受 `""`、`quiet`、`compact`、`verbose`；空值解析为 compact。拼写错误、大小写变体及额外空白均报 `invalid messaging.report_mode`，不静默纠正或降级。

`ReportingPolicy{Mode: ...}` 提供显式的 `ShowAccepted`、`ShowThinking`、`ShowToolCall`、`ShowToolResult(isError)`、`ShowFinal`、`ShowError`、`ShowApproval`。零值 policy 等价于 compact，保证没有显式配置的 Gateway 也采用安静默认值。

## 3. ReportingPolicy 行为矩阵

| 事件 | quiet | compact（默认） | verbose |

| accepted | 否 | 是 | 否 |

| tool_error | 否 | 否 | 是 |

## 5. ChannelReporter 变更

## 6. Accepted notification 实现位置

`Gateway.Receive` 调用私有 `admit` 完成 admission，然后在锁外调用 notification：

```text
锁内：校验生命周期 / 去重 / 控制命令 / 群聊 mention admission
  → getOrCreate
  → 准备展示顺序屏障（不发送、不等待网络）
  → 非阻塞 enqueue 成功
  → dedup remember
解锁
  → ChannelReporter.OnAccepted
  → best-effort Send("🤖 已收到，正在处理……")
  → Receive 返回 nil
```

重复消息、queue full、群聊未 @、approve/reject（包括 malformed control）、空消息均没有 Accepted。Queue full 不记住 dedup key，可随后重试。

为避免快 worker 的 Final/Error/Approval 抢在 Accepted 前面，ChannelReporter 提供 `PrepareAccepted`：入队前仅预留本会话的展示屏障；入队失败立即 discard，成功后在通知发送尝试结束时释放，失败/取消也释放。正文、任务错误、审批投递等待屏障，并尊重各自 Context 的取消。

该屏障只协调消息展示，不改 Engine interface、Conversation queue 的类型/容量/FIFO 或 worker 流程。任务可以在 Accepted 网络请求期间继续执行；失败通知不会吞掉最终回答或回滚任务。

## 7. Gateway lock 是否调整

是。将原 `Receive` 中的 mutex admission 块提取为 `admit`，其 `defer Unlock` 在函数返回通知回调前完成。

- `admit` 不执行 Adapter.Send；展示屏障仅做短暂本地计数/通道 bookkeeping。
- ChannelReporter 不在自身屏障 mutex 内做网络 I/O。
- dedup check / enqueue / remember 仍原子。
- Accepted 发送慢时，另一个 Conversation 的入队、Accepted 和 Final 仍能完成；重复消息也不等待原通知。
- 已入队后，即使回调 Context 取消或 Accepted API 失败，Receive 仍返回成功；任务使用原有 Gateway 生命周期。

## 8. Tool Error suppression 语义

**Tool Error 不等于 Task Error。**

`OnToolResult(..., true)` 只表示某个工具调用失败，compact/quiet 与成功结果一样抑制。它不触发 `OnError`，不改变 Recovery、Session observation、下一轮 Provider 输入或最终 runner 返回值。

当 `AgentRunner.Run` 最终返回 error，现有 Conversation Runtime 仍发送 `❌ Agent 运行失败: ...`。Session 恢复、模型创建及持久化失败也始终可见。

真实 Engine 集成测试执行“工具失败 → Agent 读取失败 observation → 工具成功 → 最终回答/最终 Run error”，验证 compact 只有 Accepted + Final/Task Error；Session 保留工具结果，Trace 保留两次 Tool.Execute、参数和结果 preview。子智能体共享 reporter 的工具回调遵循同一策略，不开例外。

## 9. Approval 为什么始终显示

Approval 是等待用户输入的控制面，不是内部 telemetry；隐藏请求会让 Agent 等待一个用户看不到的问题。因此所有模式都发送完整审批请求，保留 approve/reject 操作信息。

`RequestApproval` 仍校验 Route，发送错误仍返回 ApprovalManager，使操作被拒绝并清理 pending request。没有改成 log-only，没有修改危险命令策略、审批 Decision 或 scope。展示顺序等待被取消时也返回 error，仍 fail closed。

## 16. 已知限制 / 停止范围

- 真实飞书 A–F 人工验收未执行，需使用用户自己的凭据和聊天环境完成；不能以 mock 通过声称真实收发已验收。
- Accepted 是 best-effort 的独立文本消息，不编辑、不撤回、不自动重发；单条 Receive 会等待自己的通知发送尝试，但不持有 Gateway 大锁。慢通知可能延后本 Conversation 的可见回复/审批；其他 Conversation 不受影响。失败时后续输出照常发送，不能保证用户必定收到 Accepted。
- 展示顺序保护保证本进程先完成 Accepted 发送尝试，再投递本会话正文/错误/审批；不提供跨平台网络的额外排序、重试或 exactly-once 保证。入队和 dedup 仍是既有进程内状态，重启不保证平台重试不再通知。
- 正文沿用 `OnMessage` 语义，所有现有模型正文事件都保留；不修改 Engine 对带 ToolCalls 的模型正文事件分类。Final/错误展示策略不代表运输层必达，普通发送失败仍沿用现有日志语义。
- quiet/compact 只过滤聊天 telemetry，不脱敏模型最终正文或审批参数，不删除 Session/Trace 中的敏感工具资料。
- 全 Messaging 使用同一启动配置，修改需重启；不做 per-channel/per-conversation 模式、`/verbose` 等命令、Message Update、进度卡片、Telegram Adapter 或 M6。
