## 3. idle timeout config 设计

合并进现有全局 `config.json`，保留模型和 channels：

```json
{
  "messaging": {
    "report_mode": "compact",
    "conversation_idle_timeout": "30m"
  }
}
```

- `MessagingConfig.ConversationIdleTimeout` 是 JSON 字符串，不暴露 duration 的数字编码。
- `MessagingConfig.IdleTimeout() (time.Duration, error)` 是配置边界：缺失/空字符串 → 30m；`"0"` → disabled；正值经 `time.ParseDuration` 解析；负数、非法值、溢出均报错。标准零 duration（如 `"0s"`）同样禁用。
- `Load` / `Save` 均验证；数字 JSON 类型被现有严格 reader 拒绝。失败 Save 不覆盖原文件。
- CLI 向 Gateway 传入已解析的 `Config.ConversationIdleTimeout time.Duration`。直接调用 Gateway 时 0 明确表示禁用，不在 Gateway 内隐式补默认值；负 duration 被拒绝。
- `claw gateway -check-config` 显示 duration / disabled，仅离线验证，不创建 Session/writer、不启动 timer、不连接通道、不探测 Sandbox。配置修改需重启，Demo 行为不变。

## 4. Conversation lifecycle state 设计

```text
create → Active → queue drained / process returned → Idle
              ↑                                  │
              └──────── new admission ────────────┘
                                                 │ timeout
                                                 ▼
                                             Evicting
                                                 │ Session.Close
                                                 ▼
                                               Removed
```

`activitySeq uint64`、`closing bool`、`closed chan struct{}` 统一归 `ConversationManager.mu` 保护；`c.mu` 仍只用于 session pointer / actual Session ID 的并发访问。只有 worker 在退出时关闭 `closed`，没有额外的 lifecycle mutex 或通用 Actor 抽象。

`ConversationCount()` 继续读取同步后的 map 长度，包含尚未 Close 完的 Evicting 条目；关闭完成才减为 0，包括全局 Shutdown 的关闭路径。

## 5. queue admission 如何重构

Gateway 不再持有 Conversation pointer 向 queue 写入，改为 `ConversationManager.enqueue(ctx, msg)`：

1. 在 manager.mu 下检查 Gateway / callback context。
2. lookup 或创建唯一 Conversation，检查 closing。
3. `PrepareAccepted` 只预留展示顺序，不发送、不等待网络。
4. 非阻塞写入固定容量 64 的 queue；成功才推进 activitySeq。
5. 返回 notifier；失败撤销展示预留或直接返回 transient error。

Gateway 原有全局 admission lock 保留：dedup check → command → group admission → enqueue → **成功后 remember** 仍是一个原子 admission。Accepted 在两把锁都释放后发送。QueueFull、closing、已取消 admission 不记 dedup；重复 update 不推进 activitySeq、不多发 Accepted。

## 6. activitySeq 如何避免 race

worker 准备 idle 时，在 manager.mu 下检查 queue empty 并记录 expectedSeq。成功 enqueue 与 seq++ 处于同一个临界区。timer 到期后重新检查 map identity、closing、expectedSeq 和 queue。

即使出现 `snapshot → enqueue → queue 又变空 → 旧 timer`，seq mismatch 仍使 eviction 失败。测试专门构造这一交错，不能只靠 `len(queue)==0` 获得同样保证。

## 7. beginEviction / finishEviction 流程

- **A：beginEviction**：锁内确认 parent 未取消、map 仍指向当前 c、非 closing、seq 匹配、queue empty；只设置 closing，不删除条目。
- **B：closeRuntime**：worker 停止 timer，锁外关闭 Session，记录 close error。closing 条目此时仍阻止同 Route 创建第二个 runtime。
- **C：finishEviction**：锁内按 pointer identity 删除条目，关闭 c.closed；随后 worker Done。即使 Close 报错也移除 runtime，不留 zombie。

只有成功的 idle eviction 记录 started/completed 日志，字段仅 channel、reason、active count，不输出 ChatID、UserID 或消息内容。Close 失败沿用错误日志与 errors.Join 聚合。

## 8. Session.Close 发生的位置

`run` 的唯一退出清理调用 `closeRuntime`，同时服务于 idle eviction 和 Gateway cancellation。timer 在清理前 Stop/Drain；Session.Close 在 manager.mu / Gateway admission lock **之外**执行，每个正常 runtime 一次。Close 完成后才 finish/remove；worker WaitGroup 覆盖整个清理。

runner/reporter 不缓存到其他地方；下次创建新的 Conversation，重新 Resolve Session、调用 RuntimeFactory，得到新的引擎。Durable Session 文件不删除、不迁移。

## 9. closing 时新消息如何处理

返回 `ErrConversationClosing = errors.New("conversation is closing; retry message")`，既不向旧 queue 入队，也不创建第二个 writer；不发送 Accepted、不记 dedup、不等待 Close。

Telegram 保持 handler error 不推进 offset 的既有契约；Feishu 保持现有 handler-error retry contract。平台重投成功才 Accepted。慢 Close 的测试中，A 继续持有 writer，B 能独立完成 admission 和 Run，证明关闭没有占用全局 admission/map lock。

## 10. Approval 为什么不会被误 eviction

`process()` 同步执行完整 runner.Run；工具、Subagent、ApprovalService.Check / ApprovalManager.Wait 都在 Run 调用栈内。worker 在 process 期间停止 timer，不查询 pending approval，不新增 HasPending 等 API。

真实 Engine + Registry middleware + ApprovalService 测试等待超过 idle timeout，观察到审批通知、Conversation 仍存在、writer 仍占用、假危险工具未执行。通过 Command Router 发送 approve 后，工具才执行、Run 返回，然后才 idle eviction。late approve 仍 consumed but unmatched，不创建 Conversation。

## 11. Durable Resume 如何验证

真实 FileStore + SessionService：

1. 第一条 `remember CODE-123`，运行中另一个 FileStore/SessionService Resume 返回 ErrInUse。
2. 完成后 idle eviction；旧 Session.Append 返回 ErrSessionClosed，count=0。
3. 独立 service Resume 成功，看到已提交的 User + Assistant，证明 writer 已释放。

## 18. 已知限制 / 停止范围

- 真实平台人工验收尚待执行；本轮自动化不证明公网连接、SDK 平台重试时延或聊天气泡表现。
- closing 采用明确 transient failure，不在 Gateway 内等待；依赖 Adapter 既有重投契约，可能出现短暂重试延迟。暂不提供 durable inbox / outbox 或 exactly-once；现有进程内 queue / dedup / Telegram offset 的崩溃窗口不变。
- 不强制中断长期 Run、Tool、Subagent 或 Approval；它们属于 Active，需原有取消/超时机制结束。Session.Close 本身若永久阻塞，Shutdown 仍会等待真实释放，不能提前放弃 writer ownership。
- Close 报错会记录并聚合给最终 Shutdown，worker 仍退出、map 仍移除；不假称底层释放失败时 writer 一定可用。现有真实 FileStore 的正常释放已验证，若异常仍占用则后续 Resume 返回错误，不 fork history。
- 本轮释放 worker、Session writer 和 Conversation/engine runtime 引用，不是全局缓存/内存预算项目。SessionService 的 per-ID 锁、FileStore 的既有 snapshot/path-lock 缓存策略未修改，也不删除磁盘 Session 数据。
- 各 Chat 仍可能共用 Workspace；Session 隔离不等于文件系统隔离。已有 Feishu SDK 后台 goroutine 限制与本轮 Conversation worker 生命周期是不同问题，本轮不修改 SDK。
- 没有新 Channel、Forum Thread、Git Checkpoint、Budget、Streaming、Cancel/Steering 或其他新命令。开发到此停止，等待 Review 和人工验收。
