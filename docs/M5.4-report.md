## 3. 新 gateway 启动方式

```bash
claw gateway -workdir ./workspace
claw gateway -check-config -workdir ./workspace
```

`cmd/claw/channels.go` 负责 `channelsForMode`、enabled-channel 环境验证和 `configureChannels`。配置启用两个通道时，注册两个真实 Adapter，只创建一个 Gateway。没有启用通道会在 Workspace/Sandbox 启动前明确失败。

## 5. Adapter Supervisor 设计

`internal/gateway/supervisor.go` 为每个 Adapter 建立独立、串行的 Start/restart 循环：

```text
Start → temporary/unexpected exit → backoff → Start
      → permanent → 本通道 failed
      → Gateway context canceled → stop
```

基础退避 `1s → 2s → 4s → 8s → 16s → 30s`，附加 ±10% jitter，最终不超过 30s。一次 Start 稳定运行至少一分钟后，下一次退避重置为 1s。平台 `RetryAfter()` 提示作为最小延迟，可能超过普通 30s 上限。

一个通道失败不取消其他 Adapter、Conversation 或 Approval。只有所有通道都永久失败才返回 `errors.Join` 聚合错误。Start 意外返回 nil 也重试，不让进程无声退出或空转。

Cancel 立即中断定时器；Shutdown 等待监督循环、worker 和 Session.Close。WaitGroup 注册仍在启动锁下，保持与并发 Shutdown 的同步。

飞书适配器退出时清理 started/context/handler，允许再次 Start；关闭 SDK 自带重连，将 onError/onDisconnected 暴露给 Gateway，避免 SDK 已断线而 Start 永久不返回时无法触发监督。SDK 本身的后台 goroutine 限制见第 19 节。

## 6. Temporary / Permanent Error 规则

`internal/channel/errors.go` 提供 `PermanentError`、`Permanent(err)`、`IsPermanent(err)`，保留标准 errors.Is / errors.As / Unwrap 语义。

- Temporary：网络/超时、HTTP 5xx、429、408/425、可恢复 admission 错误、意外 clean exit。
- Permanent：无效本地配置/token 格式、Telegram 401/404、其他不可恢复 4xx、getMe 非 bot/缺少 identity、webhook 或另一个 update consumer 冲突；飞书 SDK ClientError。
- 缺少启用通道的环境变量是启动配置错误，提前明确失败。
- 非空但无效的 Telegram Token 在 Start 内验证，而非 constructor 中阻止整个 Registry 创建。因此 Telegram token 错误时 Feishu 仍能启动。
- Telegram 429 的 retry_after 会传给通用 Supervisor；Gateway 不依赖 Telegram 错误类型。
- Telegram HTTP/JSON 错误不回显原始 URL、响应正文或 description；不跟随重定向。飞书监督错误不回显 SDK 连接 ticket。

## 7. Telegram Adapter 结构

新增 `internal/telegram/`：

- `adapter.go`：可重启 Start、offset 生命周期、纯文本 Send / 分片。
- `client.go`：net/http + Bot API、超时/响应大小限制、错误分类。
- `types.go`：最小 User / Chat / Message / Entity / Update 类型。
- `normalize.go`：平台事件转换、群聊 identity 判断、UTF-16 helper。

只实现现有 `channel.Adapter`，ID 固定为 `telegram`。不引入 Telegram SDK 或新 Go 依赖。

Start 顺序：本地 token 校验 → getMe 保存本次运行的 bot identity → getWebhookInfo → getUpdates loop。检测到 webhook 明确返回 PermanentError，绝不调用 deleteWebhook 或丢弃 updates。

已核对官方 [getUpdates](https://core.telegram.org/bots/api#getupdates)、[MessageEntity](https://core.telegram.org/bots/api#messageentity)、[sendMessage](https://core.telegram.org/bots/api#sendmessage) 契约。

## 8. getUpdates offset 策略

- Long poll timeout 30s；HTTP 请求上限 40s，bootstrap/send 上限 10s。
- `allowed_updates=["message"]`，每批最多 100 条。
- 成功 admission / 主动忽略后执行 `offset = update_id + 1`，下一次 getUpdates 确认。
- Handler 返回错误时，不越过该 update；已经成功处理的较早 update 不回退。
- 同一个 Adapter 的重启保留 offset；低于当前 offset 的重复数据忽略。
- 非文本、bot 消息及不支持的 updates 也推进 cursor，避免 poison loop。
- offset 只归当前 Start 所有；Start 的互斥 admission 保证不会有并行 poller，Send 不读写 offset。

进程重启后 cursor 从 0 开始读取 Telegram 尚未确认的数据；Session 恢复与 polling cursor 是独立机制，详见第 19 节。

## 9. Telegram InboundMessage.ID 选择

使用 `strconv.FormatInt(update.UpdateID, 10)`，不是 chat-local 的 message_id。

现有 DedupKey 按 channel/account/message ID 编码，不含 ChatID；使用 update_id 可避免不同 Chat 的 message_id 相同而误去重。同一 update 重复只执行一次；不同 Chat 的相同 message_id 均执行，已通过真实 Adapter → Gateway 测试。

## 10. private / group mention 规则

- private → ChatDirect，不要求 mention。
- group/supergroup → ChatGroup；只有实体明确指向自己的 `@username`，或 reply_to_message 的发送者是自己的 bot ID，才标记 MentionedBot。
- 同时支持匹配 bot ID 的 text_mention，拒绝不合法实体边界。
- 只移除自己经过验证的 mention，保留其他人的 mention；不凭文本里的 `@bot` 猜测实体。
- 普通未 mention 群消息仍归一化交给 Gateway，由通用 admission 拒绝，避免把群聊控制面逻辑放进 Adapter。
- from.is_bot、非文本、channel post 忽略。Forum topic 暂时不建立独立 ThreadID。
- Privacy Mode 下平台可能不投递普通群文本；人工审批请回复 bot 消息。

## 11. UTF-16 entity 处理

`utf16Range` / `utf16ByteOffset` 将 Telegram UTF-16 code-unit offset/length 转换为 Go UTF-8 字节边界。

拒绝负 offset、空/负 length、越界、整数溢出及 surrogate pair 内部边界。实体先按原文验证，再按位置移除；乱序、重复或重叠 metadata 不破坏文本。

测试覆盖英文、中文、Emoji + mention、中文 + Emoji + mention、多个/大小写 mention，以及 surrogate 中间位置与异常边界。

## 12. sendMessage / chunk 策略

只发 JSON `{chat_id, text}`，无 parse_mode / entities / keyboard / message_thread_id。

Adapter 按最多 4096 rune 分片，优先选窗口后半段的最后一个换行，否则按 rune 边界切；保留字符和换行，避免拆坏 UTF-8。空文本不请求 API。

支持与 polling/restart 并发发送。发送错误向调用者返回；不自动重发不确定成功的 sendMessage，避免额外重复。普通展示失败仍沿用 ChannelReporter 日志语义，审批发送失败仍 fail closed。

## 13. SessionKey 规则

```text
channel:telegram:account:default:chat:<Telegram chat.id>
channel:feishu:account:default:chat:<Feishu chat.id>
```

复用原有 Route.Validate / BuildSessionKey / DurableSessions / FileStore，未改变事件 schema 或 Engine 的 Session 处理。ChatID 使用十进制 int64 文本，包含群聊负 ID。ThreadID 为空，不按 Telegram forum topic 分会话。

集成测试刻意让 Feishu 与 Telegram ChatID 都为 `42`，通过同一个 Gateway 分别记忆 FEISHU-111 / TG-123；重新创建 FileStore、Service、Adapter 和 Gateway 后，通过真实 Engine 恢复各自历史，且 Shutdown 后均可再次取得 writer lock。

## 14. Approval 如何复用

Adapter 不解析 approve/reject，完整交给原 Gateway Command Router。控制命令在普通群聊 admission / FIFO queue 之前处理，能解除当前正在等待审批的 worker。

原 ApprovalManager / Service 继续使用实际 durable Session ID + TaskID；错误 Chat、错误 Channel 不能批准本会话任务。通知走不可变 Route 的 ChannelReporter，所有展示模式都可见。

Telegram 的真实 Engine + 假危险工具测试覆盖 approve/reject、错误 Chat / Channel（包括跨平台相同 ChatID）、无 mention 群聊控制回复、审批后执行/拒绝 observation、控制回复不产生 Accepted。没有执行任何真实危险命令。

## 15. Presentation Policy 如何复用

复用 `AgentEngine → ChannelReporter → ReportingPolicy → Delivery → Adapter.Send`。

- compact：Accepted + Final，审批始终可见。
- quiet：Final / task error / approval。
- verbose：tool telemetry + Final，不额外发送 Accepted。

Telegram 没有 reportMode 分支。Engine、Conversation、Approval、Delivery 的平台无关生产实现没有增加 Telegram 特例或接口。

## 19. 已知限制 / 停止范围

- **真实双平台收发与人工验收尚未执行**；自动化的 Feishu websocket 使用 fake transport，Telegram 使用本地 mock Bot API，不能声称账号权限、气泡或公网连接已经验证。
- **继承的 Feishu SDK v3.9.10 生命周期限制**：Start 成功后内部 `select{}` 不退出，heartbeat loop 也不检查 ctx。Adapter 会显式关闭 socket（最多等待 5s），Gateway 不阻塞等待这些上游后台 goroutine；反复断线重启仍可能累积 SDK goroutine，直到 CLI 进程退出。本轮没有 fork/vendoring/重写 SDK；持续故障环境应监控并重启进程。Live SDK 自身的并发清理行为不由 mock race 测试保证。
- Telegram offset 和 Gateway dedup/普通任务队列仍是进程内状态，未提供持久 inbox 或 exactly-once。进程在入队、确认 update、提交工具副作用之间崩溃可能丢失未执行的排队任务或再次处理未确认 update；Durable Session 只保证已提交历史，不是消息事务。
- sendMessage/Feishu Send 沿用 best-effort，无 durable outbox、编辑或不确定发送自动重试。长文本分片也不是原子投递；速率限制可能使普通回复或审批发送失败。
- 每平台只有一个 default account，配置修改需重启；更换 bot/account 凭据前应考虑该 default namespace 已有历史。不做跨平台身份绑定、Topic Session、用户授权或管理员审批角色。
- 所有会话仍可使用同一个 Workspace；Session 隔离不等于文件/执行环境互相隔离。默认使用 Docker，仅向可信用户开放机器人。
- 仅 text；无 media、Inline Keyboard、Webhook 接收、消息编辑、Progress Update、Idle Eviction、Slack/Discord 或 Git Checkpoint。依赖保持不变，没有修改 AgentEngine / Conversation / Approval 来迁就 Telegram。
