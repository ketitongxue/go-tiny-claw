## 设计

### 不可变 Access Core

新增 `internal/access/policy.go`，项目内仅依赖 `channel`，不依赖 Feishu、Telegram、Config、Approval 或 Engine。

- `Scope{Channel, AccountID}` 是策略索引，不以 UserID 建全局身份表。
- `NewAuthorizer(map[Scope]Policy)` 深拷贝输入列表，构建私有集合；没有运行期 setter / reload / mutable config。
- `CanUse(InboundMessage) Decision` 与 `CanApprove(InboundMessage) Decision` 返回 `Allowed` 和 typed `Reason`。拒绝原因包括 policy_not_found、missing_user_id、user_not_allowed、group_not_allowed、not_approver、invalid_chat_type，不用自由文本驱动逻辑。
- nil / zero Authorizer 或缺失 scope 一律拒绝。Gateway 未注入 Authorizer 时，为构建前已注册通道的 `default` account 显式构造 open 策略，兼容原有装配；其他 account 需要显式策略。
- ID（包括查找时的 UserID / ChatID）仅 `TrimSpace`、集合去重，不改变大小写。不会回退到 UserName、ChatID 或 mention。
- 输入 map / slice 和 `OpenScopes()` 返回的快照都无法修改运行中的策略；并发测试在修改构造输入的同时执行授权查询。

### 模式与配置

`ChannelConfig.Access` 包含 mode、operators、approvers、group_chats，不含凭据。

| 模式 | 普通访问 | 审批 |
| --- | --- | --- |
| 缺失 / 空字符串 / open | 保持旧行为 | 保持旧行为 |
| restricted 私聊 | UserID 必须属于 Operators | 普通访问通过且 UserID 属于 Approvers |
| restricted 群聊 | UserID 属于 Operators，且 ChatID 属于 GroupChats | 同左，再检查 Approvers |

Load / Save / CLI 启动与直接构建 Authorizer 均验证：

- 未知 mode、空白 ID、Approvers 非 Operators 子集均报错；错误不回显身份 / 无效配置值。
- restricted Operators 不能为空；空 Approvers 合法但禁止所有人工审批，空 GroupChats 合法但仅允许私聊。
- 采用原有严格 JSON reader，未知字段、错误类型、重复 JSON 字段仍拒绝。
- 配置保留原始列表以供往返保存，运行策略使用规范化集合。`model set` 不丢 access、channels、report mode、idle timeout 等配置。
- 验证也覆盖 disabled channel，避免开启时才发现潜在错误。Runtime 注册检查仍在授权前，disabled channel 不会通过 Gateway。
- 旧 `-mode feishu` 只启用飞书，但保留其配置中的 Access，不会将 restricted 意外重置为 open。
- 已注册 open scope 在 Gateway 构建时警告一次；未启用 / 未注册的通道不警告。没有每条消息重复警告。

推荐配置见 [README](../README.md#messaging-access-control)。策略修改需重启 Gateway。

### Gateway 顺序

```text
validate message
  → registered channel check
  → CanUse
  → existing dedup / commandRouter
  → existing group mention admission
  → Conversation enqueue
  → Resolve Session / acquire writer / factory / Agent Run
```

未授权普通消息直接返回 nil，平台可 acknowledge，但不进入 dedup、不创建 Conversation / Session、不获取 writer、不发送 Accepted、不执行 Factory / Runner。

commandRouter 识别 approve / reject 后，必须调用自己的 `CanApprove`，未授权仍返回 consumed。只有授权成功且格式恰好为两个字段，才使用既有实际 SessionID + TaskID 调用 `ApprovalManager.Resolve`。Malformed control 不会成为普通 prompt；无匹配请求的合法控制命令也不创建 Conversation。

审批始终在普通任务 enqueue 之前，不进入 FIFO：即使 worker 等待审批且普通队列已经满，合法 Approver 仍能立即解除等待。Route → actual SessionID（含 legacy 飞书 ID）→ TaskID 的隔离不变；Access 增加 sender/chat 授权，但没有把平台 UserID 塞进 ApprovalManager Key。

### 日志与边界

Access 拒绝日志仅包含 channel、account、typed reason，不包含 raw UserID、ChatID、消息正文、message ID 或 token。Open 警告明确推荐 restricted。

**Human Approval != User Authorization。** Access 控制提交人与审批人；Human Approval 确认具体操作；Sandbox / Executor Policy 限制实际工具权限。三者不能互相替代。Open 继续允许原有用户行为，不能视为已经部署用户授权。

## 测试覆盖

### Access / Config

- Direct / Group 的 Operators 与 GroupChats AND 规则、空组列表、空 Approvers。
- 相同 ID 文本的跨 Channel / Account 隔离、未知 scope、nil / zero Authorizer fail closed。
- 缺失 / 空白 UserID、冒用 UserName / ChatID 不授权、Feishu ID 大小写保持。
- TrimSpace、重复 ID 集合去重、构造输入深拷贝与并发只读。
- open 默认和显式 open、未知 mode / 字段、错误 JSON 类型、空白 ID、Approver subset。
- Load / Save round trip、失败 Save 不覆盖原配置、真实 `model set` 后保留 Access。新增列表字段使 Config 不再可直接用 `==` 比较；既有配置测试改为 `reflect.DeepEqual`，保留完整相等断言，没有删减验证。
- 旧 Feishu 入口保留 restricted、非法 Access 离线启动失败且不创建 workspace。

### Gateway / Approval / M5.5

- restricted Direct / Group 授权：runner count、factory count、ConversationCount、Accepted count。
- 未授权消息：Session resolver 0 次、writer acquire 0 次、Factory / Runner 0 次、SessionStore 无新 Session、无平台回复、无 dedup 污染。
- Operator 但非 Approver 不能 approve / reject；其命令消费且不进入 prompt。空 Approvers 在取消前无法放行。
- 正确 Approver + 错 Chat / Channel / Account / Thread / Task 无法解除原请求；这些 scope 本身均可有合法访问权限。
- 真实审批等待 + 满普通队列 + 无 mention 控制：未授权无法解除，合法 Approver 可 approve / reject 并继续 FIFO；后续 idle eviction、late control 不创建 runtime。
- Malformed control（approve、reject、approve a b、reject a b）在各种权限下均 consumed。
- Command Router 单独使用时缺少 Authorizer 也 fail closed。
- restricted create → idle → evict → resume 保留历史，未授权消息不能触发重新创建 / 恢复。
- 已有 legacy SessionID 审批与重启回归升级为 restricted，仍使用实际 SessionID。
- 既有 M5.5 文件 writer 释放、真实 Engine 审批等待、eviction/admission race、Close 错误聚合、去重、presentation、adapter supervisor 回归均保留。

## 限制与停止点

- 不改变现有 Session/Workspace 隔离能力；同群共享历史、不同 Chat 可能共用 Workspace，allowlist 不是细粒度文件权限。
- Access 配置不可热更新；平台 sender 身份由 Adapter 的可信事件源提供，Core 不重新认证平台 token。
- Open 是显式兼容风险，不自动保护旧部署。无 Approver 时危险操作只能等待超时 / 取消，属于合法 fail-closed 行为。
- 持久化去重、Telegram durable cursor、Slack、Git Checkpoint、M7 / M8 均不在本次范围。
